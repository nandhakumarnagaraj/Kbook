1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
The role model is real and enforced in depth. `UserRole` has exactly three values
(OWNER, SHOP_STAFF, KBOOK_ADMIN) and three independent layers agree on them:
server URL rules (`SecurityConfig`), server method annotations (`@RequireRole` +
`RequireRoleAspect`), and client gates (Android `SessionManager`/`PermissionManager`,
web-admin `roleGuard` + `session.role`). Four role/surface combinations exist and all
four were verified from code, not assumed:

  * Android = OWNER + SHOP_STAFF      (KBOOK_ADMIN cannot use the POS: MainActivity:82)
  * Web admin = OWNER + KBOOK_ADMIN   (SHOP_STAFF is rejected at login: AuthServiceImpl:92-102)
  * Server = the authority for all of them (URL rules + @RequireRole + permission keys)

No cross-tenant read/write hole was found in the paths I traced. Tenant scoping is
performed at the query level (`findByIdAndRestaurantId`, `requireTenant()`), and the
payment surface — which has no URL-level role rule — compensates with explicit
in-service checks (`PaymentController.requireScopedBill`, `requireOwnedRestaurantId`).

The real problems are not authorization holes but (a) *orphaned server capability*,
(b) a *thin platform-admin console*, and (c) *documentation that contradicts the
running system*. Concretely:

  1. Five server feature families have no client at all: /business/commerce,
     /business/financing, /business/customers, /business/tax, /business/onboarding
     (§4-F1). Owners cannot reach them; no role can.
  2. KBOOK_ADMIN has 12 /admin/* controllers but only 3 web pages (§4-F2). Support
     work — inspect a tenant, correct a bill, view commission/reports/routing — is
     impossible; only suspend/activate, flags, KYC download and raw push exist.
  3. docs/ARCHITECTURE.md still states inventory was removed (§4-F3) while server
     /inventory/** and the web Inventory page are live and the bill-finalisation
     deduction pipeline runs automatically. (docs/meta/AGENTS.md was corrected
     earlier today; ARCHITECTURE.md was not.)
  4. One dead sync endpoint (/sync/stocklog) whose only client was removed, plus a
     server entity still mapped to `stock_logs` (§4-F4).
  5. Graphify is stale (2026-10-05 vs commits on 2026-10-13) and its mandated
     refresh command fails in this environment (§4-F5), so it must not be trusted
     for current-state questions.

Also worth stating plainly: the earlier cross-check work in this session
(FEATURE_CROSS_CHECK_AND_SOLUTIONS.txt) closed two real defects I re-verified in
this audit — the recipe endpoint sent a lazy proxy instead of the ingredient name
(fixed: RecipeDtos.RecipeLineResponse) and a refund precision check rejected valid
2-decimal amounts (fixed: BusinessReadService.java:293). Both are described in §5.

3. ROLE/SURFACE VERIFICATION (what each of the four roles can actually do)
--------------------------------------------------------------------------------
3.1 Android — SHOP OWNER
  - Full POS: billing, active orders, reprint, KDS, search bill, call customer.
  - Master data: only OWNER may write — SessionManager.canWriteMasterData() == isOwner()
    (SessionManager.kt:309) and every MenuViewModel write path checks it
    (MenuViewModel.kt:180, 201, 222, 242, 263, 431, 487, 512, 565, 591, 607, 617, 1036).
  - Configuration: canWriteConfig() == isOwner() (:322); printer config is the
    exception granted to staff (:323).
  - Reports: full reports + export (PermissionManager OWNER short-circuit, :94).
  - Payments: Easebuzz onboarding, KYC/merchant-agreement upload, refunds.
  - Terminals: can activate/reclaim its own device (/sync/terminal/**, OWNER+STAFF);
    approving other devices is web-owner only.
  - NO raw-material inventory/recipes/POs anywhere in Android (grep for
    RawMaterial|ItemRecipe|PurchaseOrder|stock_movement in Android main = 0 hits).
    This matches the product statement: inventory is web-admin + server only.

3.2 Android — SHOP STAFF
  - POS only: canUsePos() = OWNER||SHOP_STAFF (:300); MainActivity:82 sends any other
    role to ROUTE_ROLE_ACCESS.
  - Permission model is fixed by role and ignores explicit DB grants:
    PermissionManager.hasPermission returns `SHOP_STAFF_GRANTED_KEYS.contains(key)`
    (:95), where the granted set is ALL_PERMISSION_KEYS minus the owner-only config
    families (:232-252). Server mirrors this (PermissionService).
  - Can: billing create/edit/discount/settle/void/refund-by-gateway, view menu,
    printer configuration, notifications, device activation, sync.
  - Cannot: menu/category/item edits (blocked with a dialog), shop profile, GST/payment
    config, staff management, manual refunds, reports export.
  - Report cancel-order has no client permission check (ReportsViewModel.cancelOrder);
    this is consistent today because `billing.void` is in the staff-granted set — see
    §4-F9, low severity.

3.3 Web admin — SHOP OWNER
  - 10 business routes, all `data: { roles: ['OWNER'] }` (app.routes.ts:40-99):
    dashboard, reports, daily-closing, orders, menu, inventory, staff, terminals,
    settings.
  - Restaurant-wide scope (not terminal-scoped) — documented intentional difference.
  - Owner-only server rules: /business/**, /business/terminals/** (SecurityConfig
    rules) plus @RequireRole(OWNER) on BusinessAdminController (24 methods) and
    InventoryController (12 methods).
  - Cannot: platform pages (/admin/* → 403 by URL rule); cannot complete Easebuzz
    onboarding from web (§4-F7).

3.4 Web admin — KBOOK ADMIN
  - Landing path /admin/dashboard (auth.service.ts:75-76); sidebar shows exactly
    3 platform links (sidebar-layout.component.ts:426-428).
  - Server grants /admin/** and /actuator/** beyond health. Works: feature flags
    (incl. per-restaurant override + audit), businesses list/detail/suspend/activate,
    sub-merchant registry, transactions, settlements, payment metrics, webhook health,
    KYC download, merchant-agreement download, admin push send.
  - Tenant selection: only as a *path parameter* on admin endpoints
    (/admin/kyc-document/{restaurantId}/**, /admin/businesses/{restaurantId}).
    There is NO "act as owner", no tenant-scoped data browser, and no impersonation —
    so a support engineer cannot see or fix a tenant's orders/menu/inventory. See §4-F2.
  - Cannot use Android POS (not an app role) and cannot use /business/** (URL rule).

F1  ORPHANED SERVER FEATURES — HIGH (product) / MEDIUM (risk)          CONFIRMED
  Roles: Web OWNER (and arguably KBOOK ADMIN as the only possible consumer).
  Impact: five complete server feature families are unreachable from every surface.
    For a restaurant SaaS, /business/tax/** (GST summary, GST report, GST report CSV,
    GST return data — TaxComplianceController.java:20-44) is a compliance workflow the
    owner pays for and cannot use. /business/customers/** (insights, churn risk,
    opt-out/opt-in/delete/export — CustomerDataController.java:19-46) is a
    data-protection surface (DPDP-style consent/erasure) with no UI at all.
  Expected: each shipped server capability is either wired to a surface or explicitly
    deferred. Observed: implemented, tested by default suite, called by nobody.
  Root cause: an API-first build order — server feature packages were implemented and
    unit/integration tested before any client page was scoped, and nothing in the repo
    tracks "shipped but unwired" (no dead-code check, no feature-flag row, no product
    register). The gap therefore cannot surface in review.
  Evidence: UnifiedCommerceController.java:12 (/business/commerce),
    FinancingController.java:13, CustomerDataController.java:13,
    TaxComplianceController.java:14, OnboardingController.java:12.
    Client-side search for these paths in web-admin `*.ts` and Android `*.kt`
    returns 0 matches (web-admin core/services/business-api.service.ts covers
    /business/*, /analytics/*, /inventory/*, /permissions/* but none of the five).
  Confidence: CONFIRMED for "no client calls it"; NEEDS RUNTIME for whether each
    endpoint behaves correctly.
  Fix / dependencies: triage per family (wire to a web page, or delete, or mark
    feature-flagged). Cheapest first: GST report CSV from the Reports page, since
    /analytics/gst-ledger already backs the on-screen GST view.
  Blast radius: web-admin only (new pages); server deletions require a deprecation
    window because Android ships on a slow release cadence.

F2  KBOOK ADMIN CONSOLE IS A THIN SLICE OF THE PLATFORM API — HIGH          CONFIRMED
  Role: KBOOK ADMIN. Also affects tenants indirectly (no in-product support path).
  Impact: 12 /admin/* controllers exist (AdminDashboard, AdminSettlement,
    AdminSubMerchant, AdminTransaction, PaymentMetrics, WebhookHealth,
    PaymentRouting, AdminReports, AdminCommission, FeatureFlagAdmin,
    DeveloperPortal, AdminNotification) but web-admin exposes 3 routes
    (app.routes.ts:22-37). Support flows that therefore require raw API/DB access:
    reading a tenant's commission/earnings, per-tenant transaction history,
    payment routing changes, and any correction of a tenant's data.
  Expected: a platform operator can (1) find a business, (2) inspect the tenant's
    operational truth read-only, (3) perform bounded support actions — with an audit
    trail. Observed: (1) and suspend/activate only; inspecting tenant data is not
    possible at all because the only tenant-scoped admin endpoints are KYC/
    agreement downloads.
  Root cause: the platform console was built for the three highest-frequency operator
    tasks (overview, business list, flags) while the rest of /admin/** grew API-first
    for internal/ops use. There is also no tenancy model for an admin to "enter" —
    TenantContext is the only scope mechanism, and a KBOOK_ADMIN token carries no
    tenant — so a support workflow has no safe primitive to stand on today.
  Evidence: server @RequestMapping("/admin/...") controllers listed above;
    web routes admin/dashboard|businesses|feature-flags only; sidebar nav
    (sidebar-layout.component.ts:426-428); admin-api.service.ts:20-114 shows the
    client wrappers that exist (settlements, sub-merchants, transactions, metrics,
    webhooks) — these ARE wrapped but only rendered on the platform dashboard.
  Confidence: CONFIRMED (routes/controllers), NEEDS RUNTIME for what each admin page
    actually renders on staging.
  Fix / dependencies: decide the support policy FIRST (see §8 decision D2). If
    read-only tenant inspection is approved, it must reuse the OWNER services with an
    explicit tenant parameter and write a SecurityAuditEvent per access — never by
    widening /business/** to KBOOK_ADMIN.
  Blast radius: web-admin + server (new admin endpoints, audit); no Android change.

F3  DOCUMENTATION CONTRADICTS THE RUNNING SYSTEM (inventory) — MEDIUM        CONFIRMED
  Roles: all (docs drive human and agent decisions).
  Impact: docs/ARCHITECTURE.md:67 and :119 state "inventory feature removed
    2026-09-29 … `sync→inventory` no longer exists". Server /inventory/** is live with
    raw_materials, item_recipes, purchase_orders, stock_movements and automatic
    deduction on bill finalisation (InventoryService.deductForFinalizedBill), and the
    web Inventory page consumes it. An engineer or agent trusting the doc would delete
    or ignore a live money-affecting pipeline. (The two defects found and fixed today
    — recipe payload and refund precision — were both in that documented-as-removed
    area.)
  Expected: one authoritative statement of where inventory lives. Observed:
    docs/meta/AGENTS.md was corrected to say "web admin + server, not an Android
    terminal feature"; ARCHITECTURE.md was not updated and still says removed.
  Root cause: one word, two features. "Inventory" was recorded as removed when the
    Android menu-item stock ledger was dropped (schema v78), then the unrelated
    web+server raw-material inventory was built under the same name. The correction
    therefore has to be applied per document, and a single-file edit (AGENTS.md) left
    the rest of the corpus contradicting it.
  Evidence: docs/ARCHITECTURE.md:67,119; docs/meta/AGENTS.md "Do NOT build" block;
    InventoryController.java:27-352; Android main contains no inventory code.
  Confidence: CONFIRMED.
  Fix: update ARCHITECTURE.md (and audit docs/meta/FEATURE_DOCS.txt,
    docs/archive/**) to the same statement; mark archived docs as archival.
  Blast radius: docs only.

F6  OWNER BILL-EDIT (web) vs ANDROID EDIT PATHS: REVERSION EDGE CASES — MEDIUM
                                                                             LIKELY
  Roles: Web OWNER, Android OWNER/STAFF.
  Impact: the owner can edit order status/payment mode from the web
    (/business/bills/{id}/status|payment-mode → BillEditService, WebAdminControllerTest
    covers the controller), and the device edits the same fields locally. The guard
    is `statusVersion` (BillSyncService.protectBillState: strictly greater = deliberate
    edit). Historically the Android pull mapper dropped statusVersion, which silently
    reverted cancels (docs/planning/cancel-status-revert-root-cause.md). MasterSyncProcessor.kt
    now carries it (line 1631-1636: `statusVersion = remoteBill.statusVersion ?: 0`) and
    BillDao.kt:1149-1159 clamps to max(local, remote), so the documented root cause
    appears fixed — but the server's protectBillState still *silently* restores status
    instead of reporting a rejected push (documented as server RC-5 in that same file;
    GenericSyncService.java:842 reports it as a failed push, which is the later
    mitigation).
  Expected: a rejected deliberate edit surfaces to the actor on both surfaces.
  Observed: server-side version guard is correct; web edits bump statusVersion via
    BillEditService; the failure-notification half depends on GenericSyncService
    failedLocalIds (present).
  Root cause (historical, now mitigated): the Android pull mapper omitted statusVersion,
    so a pulled row overwrote the local deliberate-edit signal; the server's
    protectBillState then judged the edit stale and restored the finalized status while
    still acknowledging the push. Two independent defects (client version loss, server
    silent restore) had to both be fixed; the client half is fixed
    (MasterSyncProcessor.kt:1631-1636, BillDao.kt:1149-1159) and the reporting half
    exists via failedLocalIds — but no test covers the two-writer case, which is why
    this stays LIKELY rather than CONFIRMED.
  Evidence: BusinessAdminController.java:108-127 (status/payment-mode endpoints),
    BillEditService.java:53-79 (editable sets + guards), BillSyncService.java:302-357
    (protectBillState), GenericSyncService.java:842 (failed-push reporting),
    MasterSyncProcessor.kt:1631-1636 (pull now carries statusVersion),
    BillDao.kt:1149-1159 (max(local, remote) clamp).
  Confidence: LIKELY — the code paths are present; only runtime conflict testing
    settles whether a web edit and a device cancel in the same window converge.
  Fix: no change recommended before a runtime conflict test (see §7 Q1).
  Blast radius: none proposed. If Q1 fails, the fix spans GenericSyncService and
    BillSyncService (server) plus the Android pull mapper — affecting both clients,
    existing bill statuses, and the sync contract.

F8  ADMIN PUSH HAS NO RECIPIENT VALIDATION AND NO AUDIT — MEDIUM             CONFIRMED
  Role: KBOOK ADMIN.
  Impact: POST /admin/notifications/send takes `restaurantId` from the request body and
    pushes whatever title/message it is given (AdminNotificationController.java:21-44).
    There is no existence check (a typo'd id returns success), no rate limiting, and no
    SecurityAuditService call, unlike financial writes which are audited
    (BusinessReadService.markManualRefund audits MANUAL_REFUND). Platform pushes to
    customers' phones are exactly the kind of action that should be attributable.
  Root cause: the controller began as an internal test/ops utility (it sits beside
    NotificationTestController) and was promoted to /admin behind the URL rule only.
    The audit pattern that financial writes follow (SecurityAuditService) was never
    applied to the platform-notification path.
