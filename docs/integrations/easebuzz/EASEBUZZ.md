## 1. What it is

Easebuzz is the RBI-licensed payment aggregator. KhanaBook is the **parent merchant of
record**; each restaurant is a **sub-merchant twin** onboarded under KhanaBook.

Money model:

- Customer pays into the **parent pool**.
- At settlement, Easebuzz splits the restaurant's share to the twin's bank account.
- Restaurant receives `total − commission − MDR − GST-on-MDR`; KhanaBook keeps the
  commission.
- Refunds, chargebacks and clawbacks always land on the **parent** settlement, never
  the twin.

Canonical statement of this model and all operational procedures:
[`../easebuzz-review/OPS_RUNBOOK.md`](../easebuzz-review/OPS_RUNBOOK.md).

## 3. Onboarding lifecycle

```
DRAFT
  └─ submitToEasebuzz() ──► PENDING_KYC   (Easebuzz returns submerchant_id)
        └─ OTP auto-sent ──► OTP_SENT ──► VERIFIED
              └─ KYC portal (WebView, hosted by Easebuzz)
                    └─ webhook MERCHANT_KYC_APPROVAL
                          ├─ kyc_status=true  ──► ACTIVE  (store VA account_number + ifsc)
                          └─ kyc_status=false ──► KYC_REJECTED (reason; owner may resubmit)
```

Notes verified from code and the ERA-confirmed doc:

- **One twin per outlet.** `submerchant_id` is generated by Easebuzz, never by us.
- **OTP must be verified before KYC.** The KYC dashboard URL comes from
  `/submerchant/v1/generate_kyc_access_key`.
- **CPV is Easebuzz's manual review** (1–3 business days). The
  `MERCHANT_KYC_APPROVAL` webhook is the **only** approval signal — there is no polling API.
- **Split label** is created after KYC: `sm_<id>`, and bank changes rotate to
  `sm_<id>_v1`, `_v2`, … There is no label-update API.
- **CPV submit gates** (implemented in `SubMerchantService.submitToEasebuzz`):
  `LEGAL_ENTITY_NAME_REQUIRED`, `FSSAI_REQUIRED`, `MANDATORY_FIELDS_MISSING`,
  `BUSINESS_PROOFS_REQUIRED` / `BUSINESS_PROOF_TYPES_REQUIRED`.
  The spec header in `../../specs/EASEBUZZ_CPV_HARDENING.md` still says "PLAN (not yet
  implemented)" — that is stale; the gates exist in code (verified 2026-10-17).

## 4. Payment lifecycle

1. POS requests a payment link for a bill (`/payment/initiateLink`, carrying
   `sub_merchant_id`, `udf1=billId`, `udf2=restaurantId`).
2. Customer pays on Easebuzz hosted checkout, or scans the order-specific UPI QR.
3. Easebuzz posts a webhook. The server:
   - verifies the reverse hash (`key|...|salt`) — a mismatch is a **STOP** condition;
   - drops duplicates by `txnid` + `status` (`EasebuzzWebhookEvent` unique constraint);
   - checks amount and bill mapping;
   - marks the bill paid.
4. Post-split (`/post-split/v1/create`) is fired within 24 h, target ≤ 5 min:
   - idempotent by `merchant_request_id`;
   - exactly **one** configuration entry — the restaurant's share (`total − commission`);
   - commission stays at the parent implicitly (never a `kb_commission` label).
5. Settlement is T+1; payout webhooks carry `payout_id`, UTR, `txnid`,
   `submerchant_id`, `label`, status.

Webhook endpoints (all on `PaymentController`, base `/payments/easebuzz`):
`/webhook`, `/refund/webhook`, `/sub-merchant/webhook`, `/payout/webhook` — each
accepts JSON and form-urlencoded bodies.

## 5. Refunds, chargebacks, clawbacks

| Case | Behaviour |
|---|---|
| **Refund** | Parent-initiated `/refund/v1/initiate`, idempotent by `merchant_refund_id`; value deducted from the parent settlement. No automatic split reversal. |
| **Chargeback** | Debited from the parent next cycle; `CASE_STATUS_UPDATE` + email; evidence deadline 7–10 working days. |
| **Debited-but-failed** | Reversed by Easebuzz/bank (UPI 24–48 h, cards 5–7 days). Do **not** manually refund; show "Payment Pending". |
| **Clawback** | No reversal API and no negative transfer. Adjust the twin's **future payouts** and record it in the manual clawback ledger. |

Android exposes gateway refunds (`/payments/easebuzz/refund/{billId}`) and refund-status
polling; manual refunds are web-OWNER-only (`/business/bills/{id}/manual-refund`).

## 6. Reconciliation

`EasebuzzReconciliationService` runs at **06:00 IST daily**
(`@Scheduled(cron = "0 0 6 * * *", zone = "Asia/Kolkata")`) with two passes:

1. **Payment pass** — every Easebuzz row must map to a local bill (txnid + amount).
2. **Split pass** — expected `bill.total − commission` vs actual `payout_amount`
   (fallback `amount − peb_service_charge − peb_service_tax`).

Flags: `splitMismatch`, `splitMissingSettlement`, `splitOrphan`. Manual replay:

```
GET /admin/sub-merchants/reconciliation/splits?date=YYYY-MM-DD
```

Reconciliation is off by default: `easebuzz.reconciliation-enabled=false`.

## 8. Configuration

All keys are defined in `services/server/src/main/resources/application.properties`; dev and
sandbox override the base URLs to `testpay` / `testdashboard`. Production supplies the
secrets as environment variables.

| Property | Env var | Notes |
|---|---|---|
| `easebuzz.payment-base-url` | `EASEBUZZ_PAYMENT_BASE_URL` | default `https://pay.easebuzz.in` |
| `easebuzz.dashboard-base-url` | `EASEBUZZ_DASHBOARD_BASE_URL` | default `https://dashboard.easebuzz.in` |
| `easebuzz.wire-base-url` | `EASEBUZZ_WIRE_BASE_URL` | default `https://wire.easebuzz.in` |
| `easebuzz.merchant-key` | `EASEBUZZ_MERCHANT_KEY` | required |
| `easebuzz.salt` | `EASEBUZZ_SALT` | required — hashes are `key\|...\|salt` |
| `easebuzz.return-url` | `EASEBUZZ_RETURN_URL` | hosted-checkout return |
| `easebuzz.notify-url` | `EASEBUZZ_NOTIFY_URL` | payment notify |
| `easebuzz.webhook-url` | `EASEBUZZ_WEBHOOK_URL` | registered webhook |
| `easebuzz.wire-api-key` | `EASEBUZZ_WIRE_API_KEY` | sub-merchant/split APIs |
